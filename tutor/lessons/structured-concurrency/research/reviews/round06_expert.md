## Findings

**SHOULD FIX** — Quote: *"JEP 543 (Candidate, to finalize in JDK 28)"* (end card, ch. 8)
Problem: In the JEP process, "Candidate" is an early lifecycle stage that precedes "Proposed to Target" and "Targeted." A JEP that is only Candidate has not been committed to any specific release yet, so stating a release number ("to finalize in JDK 28") reads as a settled target when the status you cite says otherwise — and this feature's history (previews in JDK 21, 22, 23/24, 25, 26, 27 without finalizing) makes a confident release date especially risky to assert on camera.
Corrected wording: "JEP 543 (Candidate — proposing finalization for a future JDK release, not yet targeted)" or simply drop the release number and say "proposed to finalize structured concurrency." Also worth a final numeric check against openjdk.org immediately before air, since JEP numbers/status for this feature have changed almost every release.

**SHOULD FIX** — Quote: *"Then it raises the error in the handler. It arrives inside an exception group, a container that can hold the errors of several tasks."* (ch. 5)
Problem: This correctly describes what an ExceptionGroup is, but omits the practical consequence a viewer needs: ordinary `except ConnectionError:` will *not* catch it, because TaskGroup always wraps failures — even a single one — in an ExceptionGroup/BaseExceptionGroup. Anyone trying to reproduce this in real code needs `except*` (PEP 654). Leaving this out risks viewers writing handler code that silently fails to catch anything.
Corrected wording: add one clause, e.g. "...a container that can hold the errors of several tasks — and even for one error, you need `except*`, not a plain `except`, to catch what's inside."

**SHOULD FIX** — Quote: *"With an error group, none are left. The first error cancels the context, and each goroutine checks the context and returns."* (ch. 7)
Problem: This states as a general property of errgroup something that is actually conditional, in a way that's inconsistent with how carefully the script caveats the equivalent Python case. In chapter 6, a full chapter is spent showing that Python's task group can only *ask* a task to stop, and a task that ignores cancellation (bare `except`) keeps running. No equivalent caveat appears for Go: a goroutine that never checks `ctx.Done()`/`ctx.Err()` leaks under errgroup exactly like the retrying task does under TaskGroup, but the script's phrasing ("each goroutine checks the context and returns") reads as a guarantee of the mechanism itself rather than a fact about these particular goroutines. This creates an asymmetric, mildly misleading impression that Go's convention is more automatic than Python's.
Corrected wording: "...and here, both goroutines check the context and return — an errgroup depends on that check, the same way TaskGroup depends on a task not swallowing its cancellation."

**NIT** — Quote: *"In 1968, Edsger Dijkstra argued against the go to statement... His essay was called..."* / end-card citation *"Dijkstra, 'Go To Statement Considered Harmful', CACM (1968)"*
Problem: Minor but directly relevant given the chapter's whole conceit is the title lineage between Dijkstra's 1968 piece and Smith's 2018 essay (which explicitly echoes the phrase in its own title). The famous phrase "…Considered Harmful" is CACM editor Niklaus Wirth's title, not Dijkstra's own wording for the submission. Not fatal to omit, but since the script leans on the parallel between the two titles, a specialist audience may notice the omission.
Corrected wording: no narration change needed, but consider a one-line on-screen note: "title given by editor Niklaus Wirth."

**NIT** — Quote: *"Smith built it into his own library, Trio..."* (ch. 4)
Problem: Doesn't name Trio's actual construct (the "nursery"), which is the standard term of art alongside "task group" in any serious treatment of structured concurrency, and is the term that appears throughout Smith's own essay.
Corrected wording: "Smith built it into his own library, Trio, calling the block a 'nursery.'"

## What holds up well
The core technical claims are correct and match canonical sources: `asyncio.gather`'s default behavior (no cancellation of siblings, immediate propagation) matches the documented and quoted text precisely; the claim that a still-running gathered task's later exception is silently dropped (not even logged) matches CPython's actual `gather()` done-callback implementation, which explicitly marks such exceptions "retrieved" to suppress the logger — this is a real, correctly-characterized gotcha, not an invented one. The cancellation-propagation mechanics for `create_task`/awaited-in-turn (only the currently-awaited task is reached) and for `TaskGroup` (all children reached) are both accurate to how `Task.cancel()` interacts with `_fut_waiter`. The bare-`except:` catching `CancelledError` is correctly tied to `CancelledError` deriving from `BaseException` since Python 3.8. The Sústrik/Smith attribution and dates match the JEP text's own historical note. The scoping caveats in chapter 6 (only tasks created via the group's own `create_task`, not about shared-data races/deadlocks) are properly hedged and not overstated. All on-screen timing numbers are internally consistent with the stated 1.0 s / 0.1 s setup and with each other.
